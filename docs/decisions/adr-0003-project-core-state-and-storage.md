# ADR-0003: 프로젝트 코어 상태, 시간 단위와 저장 경계

- 상태: 승인됨
- 결정일: 2026-09-07
- 적용 대상: W-01 프로젝트 모델, 시간 표현, 명령 실행기, 프로젝트 스키마
- 선행 결정:
  [ADR-0002: 명령 기반 편집과 세션 행동 이력](adr-0002-command-based-edit-history.md)
- 상세 설계:
  [DESIGN-0003: 프로젝트 코어 계약](../design/design-0003-project-core-contract.md)
- 후속 결정:
  [ADR-0004: 파일 기반 경량 데이터베이스 단일화](adr-0004-single-embedded-database.md)

## 배경

승인된 UI 기준선은 밀리초 단위의 가짜 상태와 전체 상태 복사로 편집 동작을 보여 준다. 이
구현은 화면 계약을 검증하는 데에는 충분하지만 실제 프로젝트에서는 가변 프레임률, 서로 다른
오디오 샘플률, 긴 프로젝트와 실패한 편집 명령을 다뤄야 한다. UI 위젯의 표시 단위와 실제
편집 시간 단위를 분리하고, 부분 변경이 남지 않는 프로젝트 상태 경계가 필요하다.

프로젝트 저장에 데이터베이스가 필요한지도 W-01에서 먼저 판단해야 한다. 프로젝트는 한
사용자가 선택한 파일 하나를 열어 전체 편집 그래프를 읽고 쓰는 문서이며, 현재 범위에는
다중 사용자 갱신, 서버 질의, 대규모 집계 또는 여러 프로젝트를 가로지르는 관계형 질의가
없다.

## 결정

### 프로젝트 시간

1. 프로젝트 타임라인 시간은 초당 `1,000,000,000`틱인 부호 있는 정수 나노초로 표현한다.
2. 지속되는 프로젝트 상태에는 부동소수점 초나 UI의 밀리초 값을 저장하지 않는다.
3. 프로젝트의 위치는 0 이상, 클립 길이는 0보다 커야 한다.
4. 프레임률과 재생 속도는 분자와 분모가 양수인 기약분수로 표현한다.
5. 프레임 번호를 시간으로 바꿀 때 이전 프레임 길이를 반복해서 더하지 않고 절대 프레임
   번호와 유리수 프레임률에서 매번 계산한다. 나노초로 정확히 표현되지 않는 값은 가장 가까운
   정수로 반올림하고 정확히 절반이면 0에서 먼 쪽을 선택한다.
6. 소스 미디어를 분석하는 W-02에서는 원본 스트림의 time base와 PTS를 별도 메타데이터로
   보존한다. 편집점은 실제 프레임 또는 오디오 샘플 경계에 스냅한 뒤 프로젝트 시간으로
   변환한다.
7. Qt의 밀리초 슬라이더, 사람이 입력하는 소수 초와 FFmpeg time base 변환은 어댑터 또는
   미디어 서비스 경계에서만 수행한다.

나노초 정수는 JSON에서 손실 없이 기록할 수 있고 일반적인 영상·오디오 경계를 충분히 세밀하게
표현한다. 유리수에서 절대 위치를 계산하므로 23.976fps 같은 프레임률에서도 프레임마다 반올림
오차를 누적하지 않는다.

### 프로젝트 상태와 명령

1. 프로젝트, 미디어 참조, 트랙과 클립은 UI 및 Qt에 의존하지 않는 불변 값 객체로 구현한다.
2. 프로젝트는 영상·사진, 음악, 내레이션과 텍스트 트랙을 각각 하나씩 가지며 트랙 종류는 UI
   기준선과 동일하게 고정한다.
3. 시각 트랙은 빈 구간 없이 이어지고, 음악·내레이션·텍스트 트랙은 프로젝트 절대 시간을
   사용한다.
4. 지속되는 프로젝트 변경은 `ProjectCommand` 경계를 통과한다. 명령은 현재 프로젝트를 직접
   변경하지 않고 검증된 다음 프로젝트와 최소 역명령을 반환한다.
5. 명령 실행기는 명령이 성공적으로 반환된 뒤에만 현재 프로젝트와 이력 위치를 한 번에
   교체한다. 예외, 거부 또는 잘못된 결과가 발생하면 기존 불변 프로젝트와 이력은 그대로다.
6. 행동 이력은 전체 프로젝트 스냅샷이 아니라 원래 명령과 그 명령이 생성한 역명령을
   보관한다. 미디어 바이트, 프레임, 썸네일과 캐시는 이력에 들어가지 않는다.
7. 실행 취소 뒤 새 명령을 실행하면 현재 위치 뒤의 재실행 이력을 제거한다.
8. 새 프로젝트와 프로젝트 열기는 새 명령 실행기 세션을 만들며 행동 이력을 직렬화하지
   않는다.

불변 모델을 사용하면 명령 준비 중 예외가 발생해도 공유 상태에 부분 변경을 남길 수 없다.
명령이 만드는 새 프로젝트는 변경된 작은 튜플과 값 객체만 교체하고, 행동 이력은 이전 프로젝트
전체를 보존하지 않는다.

### 프로젝트 스키마와 데이터베이스

1. 사용자 프로젝트는 `schema_version`을 갖는 단일 문서로 저장한다. W-01의 최초 스키마
   버전은 `1`이다.
2. 정식 파일 읽기, 원자적 쓰기와 마이그레이션 구현은 W-03 범위다. W-01은 도메인 필드와
   JSON 키, 단위 및 제외 데이터를 고정한다.
3. 프로젝트 문서는 프로젝트 ID와 이름, 출력 화면, 미디어 참조 목록, 네 개의 고정 트랙과
   클립을 포함한다.
4. 선택, 포커스, 재생 위치, 패널 상태, 미리 보기 캐시, 프록시, 출력 진행 상태와 세션 행동
   이력은 프로젝트 문서에 저장하지 않는다.
5. 현재 프로젝트 저장에는 데이터베이스를 사용하지 않는다. 전체 문서를 한 단위로 검증하고
   원자적으로 교체하는 작업에는 버전이 붙은 JSON 문서가 더 단순하고 복구하기 쉽다.
6. 향후 최근 프로젝트 목록이나 재생성 가능한 캐시 색인처럼 질의 가능한 앱 데이터가 필요하면
   별도 프로세스가 없는 SQLite를 우선 검토한다. 분석·집계 요구로 DuckDB를 검토하더라도
   SQLite와 병행하지 않고 하나의 임베디드 엔진으로 통합하거나 대체한다. 상세 선택 원칙은
   ADR-0004를 따른다. 서버형 데이터베이스는 제품의 로컬 우선 범위에 포함하지 않는다.
7. 파일 DB를 도입하는 후속 결정은 `platformdirs`의 사용자 데이터 디렉터리 아래 위치, 스키마
   마이그레이션, 백업과 손상 복구 정책을 함께 기록해야 한다. 사용자 프로젝트 파일 옆에
   숨은 DB를 자동 생성하지 않는다.

## 프로젝트 문서의 안전 경계

W-03은 이 결정과 DESIGN-0003을 기준으로 다음 순서를 구현한다.

1. 파일 전체를 별도 메모리 객체로 파싱한다.
2. `schema_version`과 모든 도메인 불변식을 검증한다.
3. 지원하는 이전 버전은 원본과 다른 임시 사본에서 순차 마이그레이션한다.
4. 저장은 같은 디렉터리의 임시 파일을 완전히 기록하고 동기화한 뒤 대상 파일을 원자적으로
   교체한다.
5. 더 새로운 스키마, 알 수 없는 필수 값 또는 손상된 문서는 현재 프로젝트를 바꾸지 않고
   읽기를 거부한다.
6. 자동 저장과 충돌 복구는 W-10에서 정상 저장본을 덮어쓰지 않는 별도 파일로 구현한다.

W-03에서 위 경계를 `src/movie_maker/project/persistence.py`와 실제 Qt 저장·열기 흐름으로
구현했다. 확정된 스키마와 실패·취소 시 세션 불변 계약은
[DESIGN-0005](../design/design-0005-project-persistence-contract.md)에 기록한다.

W-04는 스키마 1을 유지한 채 source 범위와 유리수 재생 속도로 클립 길이를 검증하고, 실제
프레임률·샘플률·time base 우선순위에 따라 편집점을 결정적으로 스냅한다. 시각 트랙은 명령
결과마다 연속 위치를 다시 계산하고 보조 트랙은 절대 위치를 유지한다. 상세 계약은
[DESIGN-0006](../design/design-0006-timeline-editing-contract.md)에 기록한다.

## 결과

### 장점

- UI 표시 정밀도와 코어 편집 정밀도가 분리된다.
- 고정 프레임률과 가변 프레임률 모두 같은 프로젝트 시간축을 사용할 수 있다.
- 실패한 명령의 원자성을 전역 상태 복사 없이 보장할 수 있다.
- 프로젝트 파일이 사람이 진단할 수 있는 단일 문서로 남고 별도 DB 관리가 필요 없다.
- 이후 하나의 임베디드 DB가 필요한 앱 데이터와 사용자 프로젝트의 수명주기를 명확히 분리한다.

### 비용과 제약

- UI와 FFmpeg 경계에서 단위 변환 및 명시적인 반올림이 필요하다.
- 불변 컬렉션을 변경할 때 새 튜플을 만들므로 대규모 프로젝트 성능을 계측해야 한다.
- W-01의 스키마는 저장 구현 전 초안이므로 W-02의 실제 미디어 메타데이터 결과에 따라
  호환 가능한 필드가 추가될 수 있다.
- 명령 병합과 이력 메모리 제한은 실제 프로젝트 계측 전까지 보류한다.

## 제외한 대안

### 부동소수점 초 또는 정수 밀리초

부동소수점은 직렬화와 반복 계산에서 결과가 달라질 수 있고, 밀리초는 60fps 프레임 및 오디오
샘플 경계를 표현하기에 거칠어 제외한다.

### 프로젝트마다 SQLite 또는 DuckDB 사용

현재 프로젝트는 부분 질의보다 전체 그래프 검증과 원자적 교체가 중요하다. DB 파일은 스키마
관리, 백업과 손상 복구 경로를 추가하지만 현재 요구에는 대응하는 이점이 없어 제외한다.

### 명령 실행 전 프로젝트 전체 복사

원자성 구현은 단순하지만 긴 프로젝트에서 메모리 비용이 커지고 ADR-0002의 최소 역정보
원칙과 맞지 않아 제외한다.

## 검증 기준

- 유리수 프레임률을 긴 구간에 변환해도 반복 덧셈 오차가 누적되지 않는다.
- 프로젝트와 하위 모델이 생성 시 모든 식별자, 시간, 트랙 및 참조 불변식을 검증한다.
- 성공한 명령만 행동 이력에 기록된다.
- 명령 실행, 실행 취소와 재실행 중 실패하면 프로젝트와 이력 위치가 바뀌지 않는다.
- 실행 취소와 재실행 왕복이 동일한 프로젝트 값을 만든다.
- 실행 취소 뒤 새 명령을 실행하면 재실행 후보가 제거된다.
- 프로젝트 코어는 PySide6, 파일 시스템, 데이터베이스 또는 FFmpeg를 import하지 않는다.
