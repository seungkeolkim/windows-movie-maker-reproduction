# ADR-0002: 명령 기반 편집과 세션 행동 이력

- 상태: 승인됨
- 결정일: 2026-09-06
- 적용 대상: 프로젝트 변경, 편집 코어, UI 배선, 실행 취소·다시 실행
- 관련 기능:
  [PRODUCT-0002의 F-TIMELINE-11 및 F-TIMELINE-12](../product/product-0002-feature-inventory.md)

## 배경

MVP에서는 클립 추가, 이동, 삭제, 분할, 트리밍, 사진 길이와 영상 속도 변경처럼 프로젝트
상태를 바꾸는 기능을 구현한다. 사용자에게 실행 취소와 다시 실행을 제공하는 시점은
1.0이지만, MVP에서 각 위젯과 서비스가 프로젝트 상태를 직접 변경하면 나중에 행동 이력을
도입할 때 모든 편집 경로를 다시 작성해야 한다.

프로젝트는 원본 미디어를 변경하지 않는 비파괴 편집을 원칙으로 한다. 동일한 편집 행동을
안전하게 되돌리고 다시 적용하려면 변경 전후의 의미, 실행 순서와 현재 이력 위치를 편집
기능을 처음 구현할 때부터 일관된 구조로 다뤄야 한다.

## 결정

1. 프로젝트의 지속적인 편집 상태를 바꾸는 사용자 행동은 명령 경계를 통해 실행한다.
2. UI 위젯은 프로젝트 모델을 직접 변경하지 않고 컨트롤러 또는 명령 실행기에 사용자 의도를
   전달한다.
3. 명령 실행기는 명령을 적용하고 성공한 명령만 세션 행동 이력에 기록한다.
4. 각 명령은 실행에 필요한 입력과 안전하게 되돌리는 데 필요한 이전 값 또는 역연산 정보를
   보관한다.
5. 행동 이력은 실행된 명령의 순서와 현재 위치를 관리하여 되돌리기와 재실행을 지원한다.
6. 과거 명령을 되돌린 뒤 새로운 편집 명령을 실행하면 기존 재실행 후보는 제거한다.
7. 명령이 실패하면 프로젝트가 부분적으로 변경된 상태를 남기지 않는다.
8. MVP에서는 명령 실행, 되돌리기, 재실행과 세션 행동 이력의 내부 계약 및 배선을 구현한다.
9. 실행 취소·다시 실행 버튼, 메뉴, 단축키와 사용자 피드백은 1.0 기능으로 노출한다.
10. 프로젝트 저장 파일은 현재 편집 결과를 보관한다. MVP에서는 행동 이력을 저장 파일에
    직렬화하거나 앱 재시작 이후까지 복원하지 않는다.

명령 경계에 포함되는 대표 행동은 다음과 같다.

- 미디어 보관함에 항목 추가 및 제거
- 타임라인 클립 추가, 이동, 삭제, 분할, 트리밍과 복제
- 사진 표시 시간과 영상 재생 속도 변경
- 오디오 배치와 편집 설정 변경
- 제목, 전환과 시각 설정 변경

다음 동작은 프로젝트의 지속적인 편집 결과를 바꾸지 않으므로 기본 행동 이력에 넣지 않는다.

- 선택, 포커스와 패널 열기 또는 닫기
- 재생, 일시 정지, 재생 헤드 탐색과 타임라인 확대
- 프로젝트 저장과 다른 이름으로 저장
- 미리 보기용 캐시, 썸네일, 파형과 프록시 생성
- 동영상 출력과 진행 상태

새 프로젝트와 프로젝트 열기는 현재 세션의 경계를 만든다. 기존 행동 이력을 비우기 전에
저장하지 않은 변경을 처리하며, 프로젝트를 연 뒤에는 빈 행동 이력에서 시작한다.

## 구현 경계

이 결정은 특정 Python 클래스 이름이나 직렬화 형식을 확정하지 않는다. 구현 설계에서는
최소한 다음 역할을 분리한다.

- **편집 명령:** 하나의 사용자 의도와 되돌리기에 필요한 정보
- **명령 실행기:** 명령 적용의 단일 진입점과 성공·실패 처리
- **행동 이력:** 실행 순서, 현재 위치, 되돌리기 및 재실행 가능 상태
- **프로젝트 모델:** 명령이 변경하는 현재 비파괴 편집 상태
- **UI 어댑터:** 사용자 의도를 명령으로 변환하고 변경된 상태를 화면에 반영

명령이 프로젝트 모델의 내부 구현 전체를 알거나 UI 위젯을 참조하지 않게 한다. 대용량
미디어 데이터나 프레임 이미지를 행동 이력에 복제하지 않고 편집 상태를 복원하는 데 필요한
최소 정보만 보관한다.

## 결과

### 장점

- 1.0에서 실행 취소·다시 실행 UI를 추가할 때 기존 편집 기능을 다시 배선할 필요가 줄어든다.
- 같은 편집 행동을 목업, UI, 테스트와 실제 서비스에서 일관된 경계로 호출할 수 있다.
- 모든 프로젝트 변경이 한 경로를 지나므로 비파괴 편집 규칙과 상태 검증을 적용하기 쉽다.
- 실패한 명령의 원자성과 행동 이력 분기 규칙을 집중적으로 테스트할 수 있다.

### 비용과 제약

- 사용자에게 실행 취소 UI를 제공하지 않는 MVP에서도 명령과 이력 기반을 먼저 구현해야 한다.
- 단순한 속성 변경도 이전 값과 실패 복구를 고려해야 하므로 초기 코드가 늘어난다.
- 명령이 외부 파일이나 장시간 작업을 직접 소유하지 않도록 경계를 세심하게 나눠야 한다.
- 행동 이력의 메모리 제한과 명령 병합 정책은 실제 사용량을 측정한 뒤 추가로 결정해야 한다.

## 제외한 대안

### UI 위젯에서 프로젝트 상태 직접 변경

초기 구현은 단순하지만 편집 경로마다 되돌리기 규칙이 흩어지고 1.0에서 대규모 재작성이
필요하므로 제외한다.

### 매 변경마다 프로젝트 전체 스냅샷 저장

구현은 이해하기 쉽지만 긴 프로젝트에서 메모리 사용량이 커지고 외부 미디어 상태와
백그라운드 작업을 불필요하게 복제할 수 있어 기본 방식으로 사용하지 않는다.

### MVP부터 행동 이력을 프로젝트 파일에 저장

세션을 넘어 실행 취소를 유지할 수 있지만 프로젝트 스키마, 호환성과 파일 크기를 복잡하게
만든다. MVP에서는 현재 결과만 저장하고 지속적인 행동 이력은 별도 요구가 생길 때 다시
검토한다.

## 검증 기준

- 각 프로젝트 변경 명령을 실행한 뒤 되돌리면 이전 상태와 같아진다.
- 되돌린 명령을 재실행하면 최초 실행과 같은 편집 결과가 된다.
- 여러 명령의 실행 순서와 현재 이력 위치가 일관되게 유지된다.
- 되돌린 뒤 새 명령을 실행하면 이전 재실행 후보가 제거된다.
- 실패한 명령은 프로젝트와 행동 이력 어느 쪽에도 부분 결과를 남기지 않는다.
- 저장 후 다시 연 프로젝트는 저장 시점의 결과를 보존하고 빈 행동 이력으로 시작한다.
- UI 테스트는 위젯이 모델을 직접 변경하지 않고 명령 경계를 호출하는지 확인한다.
