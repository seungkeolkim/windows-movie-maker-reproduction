- UI 기준선: [MOCK-0003의 UI-MOCK-BASELINE-1](../mock/mock-0003-review-log.md)

## 목적

이 문서는 목업의 `MockProjectState`와 `_execute_edit`를 실제 서비스로 교체하기 전에 UI와
독립적인 프로젝트 코어 계약을 고정한다. W-01에서는 시간과 클립 상태, 명령 적용 및 세션
이력을 구현한다. 실제 파일 선택·분석, 프로젝트 파일 I/O, 디코딩, 오디오 처리와 FFmpeg
출력은 각각 W-02 이후 작업에 남긴다.

## 모듈 경계

프로젝트 코어는 `src/movie_maker/project/` 아래에 둔다.

| 모듈 | 책임 | 의존하지 않는 대상 |
| --- | --- | --- |
| `time.py` | 나노초 시간, 유리수 프레임률과 결정적 반올림 | Qt, FFmpeg |
| `model.py` | 미디어 참조, 출력 화면, 클립, 고정 트랙과 프로젝트 불변식 | UI, 파일 시스템 |
| `commands.py` | 편집 명령, 역명령과 원자적 세션 행동 이력 | UI, 저장, 미디어 바이트 |
| `__init__.py` | 외부에서 사용할 안정적인 코어 이름 노출 | 구현 세부사항 |

UI는 이후 작업에서 사용자 의도를 명령으로 변환하고 실행기의 현재 프로젝트를 화면 모델로
표현한다. 선택, 재생 헤드와 대화상자 상태는 프로젝트 코어에 넣지 않는다. 기존
`MockController`는 W-02~W-07의 실제 서비스가 준비될 때까지 승인된 UI 상태를 재현하는 개발
목업으로 유지한다.

## 시간 계약

### 기본 단위

- `ProjectTime`은 부호 있는 정수 `nanoseconds` 하나를 가진 불변 값 객체다.
- 초당 틱 수는 `1_000_000_000`으로 고정한다.
- 도메인 모델의 시작 위치와 소스 시작은 0 이상이어야 한다.
- 클립 및 시간 범위의 길이는 0보다 커야 한다.
- 공개 변환 API는 정수, `Decimal` 또는 `Fraction`만 받으며 `float` 입력은 거부한다.

### 반올림

유리수 초를 나노초로 바꿀 때 기본값은 가장 가까운 정수이며 정확히 절반이면 0에서 먼 쪽으로
반올림한다. 필요한 경계에서는 내림과 올림을 명시할 수 있다. 같은 값은 플랫폼과 로캘에
관계없이 같은 정수가 되어야 한다.

`FrameRate(numerator, denominator)`는 초당 프레임 수를 나타낸다. 프레임 `n`의 시간은 다음
식을 한 번 계산해 얻는다.

```text
frame_time(n) = round(n × denominator × 1_000_000_000 / numerator)
```

이전 프레임 길이를 반복해서 더하지 않는다. 예를 들어 `24000/1001`fps의 24,000번째 프레임은
정확히 1,001초 위치가 된다.

## 도메인 모델

### 미디어 참조

`MediaReference`는 미디어 바이트를 소유하지 않고 다음 식별·메타데이터만 보관한다.

- 프로젝트 안에서 유일한 `asset_id`
- 사용자에게 표시할 이름과 원본 `source_path`
- `video`, `photo`, `audio` 중 하나인 미디어 종류
- 영상·오디오의 알려진 소스 길이 또는 사진의 `null`
- 영상·사진의 회전 적용 전 픽셀 크기

W-02는 실제 ffprobe 결과, 원본 time base와 스트림 정보를 이 경계에 호환 가능한 선택
필드로 추가한다. 상세 계약은 [DESIGN-0004](design-0004-media-library-contract.md)를 따른다.
원본 파일을 수정하거나 프로젝트에 복제하지 않는다.

### 클립

`Clip`은 미디어 또는 생성 콘텐츠를 타임라인에서 사용하는 비파괴 참조다.

| 필드 | 계약 |
| --- | --- |
| `clip_id` | 프로젝트 전체에서 유일한 안정적 문자열 |
| `track` | `visual`, `music`, `narration`, `text` 중 하나 |
| `asset_id` | 텍스트는 `null`, 나머지는 존재하는 호환 미디어 ID |
| `timeline_start_ns` | 프로젝트에서의 시작 위치, 0 이상 |
| `duration_ns` | 결과 타임라인 길이, 0보다 큼 |
| `source_in_ns` | 원본에서 사용을 시작하는 위치, 0 이상 |
| `source_out_ns` | 원본 사용 끝 또는 생성 콘텐츠의 `null`; 있으면 시작보다 뒤 |
| `playback_rate` | 양의 기약분수; 기본값 `1/1` |

클립 결과 길이와 소스 범위·속도의 정확한 계산, 프레임 스냅 및 트리밍 규칙은 W-04에서 명령으로
추가한다. W-01 모델은 계산 결과가 지켜야 할 기본 불변식을 검증한다.

### 트랙과 프로젝트

프로젝트는 다음 순서의 트랙을 정확히 하나씩 가진다.

1. `visual`: 영상·사진 미디어, 빈 구간 없이 순차 배치
2. `music`: 오디오 미디어, 절대 시간 배치
3. `narration`: 오디오 미디어, 절대 시간 배치
4. `text`: 미디어 참조가 없는 생성 클립, 절대 시간 배치

모든 트랙은 결정적 직렬화를 위해 시작 시간 순서를 유지한다. 프로젝트는 중복 미디어 ID,
중복 클립 ID, 없는 미디어 참조, 트랙과 호환되지 않는 미디어, 잘못된 화면 크기를 거부한다.
프로젝트 전체 길이는 시각 트랙의 마지막 클립 끝으로 정한다.

## 프로젝트 스키마 초안

프로젝트 파일 확장자와 원자적 저장은 W-03에서 구현한다. 논리 문서는 UTF-8 JSON이며 시간
필드 이름에 `_ns`를 붙여 단위를 파일 자체에서 알 수 있게 한다.

```json
{
  "schema_version": 1,
  "project_id": "project-uuid",
  "name": "제주 여행",
  "canvas": {
    "width": 1920,
    "height": 1080,
    "reference_asset_id": "media-001"
  },
  "media": [
    {
      "asset_id": "media-001",
      "name": "바다.mp4",
      "source_path": "D:/Media/바다.mp4",
      "kind": "video",
      "duration_ns": 12000000000,
      "width": 1920,
      "height": 1080
    }
  ],
  "timeline": {
    "visual": [
      {
        "clip_id": "clip-001",
        "asset_id": "media-001",
        "timeline_start_ns": 0,
        "duration_ns": 5000000000,
        "source_in_ns": 2000000000,
        "source_out_ns": 7000000000,
        "playback_rate": {"numerator": 1, "denominator": 1}
      }
    ],
    "music": [],
    "narration": [],
    "text": []
  }
}
```

스키마 버전 `1`에서 필수로 고정하는 의미는 다음과 같다.

- 식별자와 열거형 값은 언어별 표시 문구가 아닌 안정적인 영문 값이다.
- 경로는 사용자가 선택한 원본 참조이며 미디어 데이터는 포함하지 않는다.
- 배열 순서는 타임라인의 의미 있는 순서다.
- 알 수 없는 `schema_version`을 추측해 열지 않는다.
- 저장 시 선택과 재생 상태, 행동 이력, 썸네일·파형·프록시, 출력 작업은 제외한다.

W-02~W-09에서 새 속성이 필요하면 기본값을 가진 선택 필드로 안전하게 확장할 수 있는지 먼저
검토한다. 기존 의미를 바꾸거나 필수 구조를 변경하면 스키마 버전을 올리고 W-03의 순차
마이그레이션을 추가한다.

## 명령 프로토콜

명령은 다음 논리 계약을 구현한다.

```text
ProjectCommand.apply(current_project)
    -> CommandApplication(next_project, inverse_command)
```

- `apply`는 입력 프로젝트를 변경할 수 없다.
- 모든 사전 조건을 검사한 뒤 새 불변 프로젝트를 만든다.
- 성공 결과에는 정확히 한 번의 실행 취소에 필요한 최소 역명령이 포함된다.
- 사용자 입력 또는 현재 상태 때문에 실행할 수 없으면 `CommandRejected`를 발생시킨다.
- 예기치 않은 구현 실패는 `CommandExecutionError`로 감싸되 원인을 보존한다.
- 프로젝트 ID 또는 스키마 버전을 바꾸는 결과와 실제 변화가 없는 결과는 실행기가 거부한다.

명령 실행기의 커밋 지점은 `apply`와 결과 검증이 모두 끝난 뒤다. 프로젝트, 이력 목록과 현재
위치를 함께 교체한다. 실행 취소는 저장된 역명령을 적용하고, 재실행은 원래 명령을 적용한다.
어느 방향이든 실패하면 프로젝트와 이력 위치를 바꾸지 않는다.

W-01은 계약을 검증할 수 있는 프로젝트 이름 변경, 미디어 참조 추가·제거와 클립 삽입·제거
명령을 제공한다. 분할, 이동, 트리밍, 속도와 리플 편집은 같은 계약을 사용해 W-04에서
추가한다.

## 데이터베이스 판단

W-01에서는 데이터베이스를 추가하지 않는다.

| 판단 항목 | 현재 프로젝트 문서 |
| --- | --- |
| 읽기·쓰기 단위 | 전체 프로젝트 그래프 하나 |
| 동시 작성자 | 로컬 사용자 한 명 |
| 필요한 질의 | ID 조회와 순서 순회, 메모리에서 처리 가능 |
| 트랜잭션 경계 | 검증된 문서 전체의 원자적 교체 |
| 재생성 가능한 대용량 데이터 | 프로젝트 밖 캐시로 분리 |

따라서 SQLite나 DuckDB도 현재는 관리 비용만 늘린다. 후속 범위에서 앱 전역 색인이 실제로
필요하면 서버 프로세스 없는 SQLite를 기본 후보로 삼고, 분석형 집계 요구가 증명될 때만
DuckDB를 검토한다. DB를 도입할 때에는 사용자 데이터 디렉터리의 정확한 위치, 마이그레이션,
백업과 손상 시 재생성 또는 복구 절차를 새 ADR에 기록한다.

- [x] `ProjectTime`과 `FrameRate`가 이 문서의 변환 및 반올림 규칙을 구현한다.

- [x] 새 코어 테스트와 기존 UI 목업 회귀 테스트가 모두 통과한다.
